# Design

## Context

动机与功能范围见 `proposal.md`，行为约束见四份 delta specs。已确认本次采用核心三项加轻量运维增强；日志仅保留当前进程的最近记录。

与实现相关的现状：

- 项目使用 Bun Workspaces。客户端是 Next.js 静态导出，已有 React、SWR、Axios；后端为 Elysia，使用 node-schedule 和 TypeORM/PostgreSQL。两端通过 `@timeline/contracts` 共享 HTTP DTO。
- `server/src/index.ts` 的统一请求钩子验证管理员 Cookie，并按敏感路由表拦截操作。时间线列表和总数目前分别根据 Cookie 决定是否包含 `is_secret`，没有独立读取视角。
- `server/src/sync/index.ts` 使用 `isSyncing` 防重入并执行 `Promise.allSettled`，只写日志而不暴露结果；`server/src/index.ts` 另用 `runningSyncTasks` 跟踪退出等待。QQ 空间缺少凭据时写错误日志后正常返回，不能直接将 Promise fulfilled 当成全部业务成功。
- `server/src/utils/logger.ts` 是统一日志入口，包含安全 URL 与错误诊断格式化，但输出端目前仅调用控制台，没有可读取的历史。
- `TimelineHome` 的列表和总数 SWR key 不包含登录身份；`RootLayout` 收到 401 后只更新登录布尔值；`TimelineItemLabel` 依据这个布尔值展示修改操作。因此，单纯增加前端过滤或将登录布尔值改为 false 都无法完整实现预览。
- Axios 默认超时为 3 秒，手动同步接口不能等待整轮同步结束。仓库已有 `@playwright/test`，未发现现成的业务测试目录或测试脚本。

## Goals / Non-Goals

**Goals:**

- 先让手动同步经同一协调器完整运行，再叠加状态与日志，最后接入预览与管理界面；每一层都可独立验证。
- 真实身份决定权限，读取视角只收窄时间线可见范围；列表、总数与客户端缓存统一遵循该范围。
- 运行状态由一个模块所有，日志保留由一个模块所有；沿用现有依赖和认证机制，不新增基础设施。

**Non-Goals:**

- 不建设队列、分布式锁、持久化运行历史或通用任务平台；本次遵循现有单后端进程部署模型。
- 不为每条远程数据或异步视频转码提供进度百分比；运行结果描述同步函数的执行结果，条目级警告仍通过日志排查。
- 不改变配置文件的管理方式，不增加管理功能开关或旧实现兼容分支。其他功能排除项见提案。

## Decisions

### 1. 使用现有客户端内的单个管理面板

采用独立 `AdminConsole` 组件。时间线在桌面和移动端统一使用右下角的图标按钮打开管理面板。桌面使用右侧抽屉，移动端使用近全屏面板。同步、日志、访客预览和退出登录集中在固定头部，仅内容区滚动。打开期间锁定页面滚动，继续使用原生模态对话框处理初始焦点、Escape、焦点约束和关闭后的焦点恢复。时间线滚过一屏后在同一区域显示回到顶部按钮，并遵从减少动态效果的系统设置。

这是基于当前项目结构选择的方案。独立管理站点会重复静态站点、登录和发布流程；将功能散落在条目菜单中又不适合运行日志和全局同步，因此均不采用。无需引入 UI 组件库。

### 2. 沿用真实 Cookie 权限，管理响应禁止缓存

在 `server/src/admin.ts` 定义管理接口处理函数，在现有 `app` 上注册路由并加入敏感路由表，避免依赖插件钩子的继承关系或复制一套认证。管理员未启用时保持现有 HTTP 400；启用后无有效会话返回 401。新接口不会向客户端返回账号、密钥、Cookie 或原始配置对象。

| 接口 | 成功结果 | 业务拒绝 |
| --- | --- | --- |
| `GET /admin/sync` | 当前同步与最近结果快照 | 400：管理员未启用；401：无有效会话 |
| `POST /admin/sync` | 202，`{ runId }` | 409：正在运行或没有启用服务；503：初始化中或正在停止 |
| `GET /admin/logs` | 按条件筛选的最近日志快照 | 400：查询参数非法；401：无有效会话 |

管理响应及时间线列表、总数响应均设置 `Cache-Control: private, no-store`。客户端 Axios 继续携带现有 Cookie，管理写操作只由明确操作触发。

### 3. 同步协调器拥有唯一的运行状态和在途 Promise

在现有 `server/src/sync/index.ts` 内提供启动、读取快照及等待当前任务结束的能力，替换原来的 `isSyncing` 和 `runningSyncTasks` 双重跟踪。启动时在任何 `await` 之前占用当前运行；一次只保留一个当前运行、一个最近已结束运行及一个在途 Promise，不建立排队机制。

所有入口均接入该协调器：手动请求、node-schedule 回调、启动时的 `FULL_SYNC`。手动入口沿用正常同步参数，不接受全量或服务选择参数；已有启动全量及服务级 `full` 行为继续作为正式同步能力使用。数据库初始化后才标记可执行，退出流程先标记停止受理，再使用现有超时机制等待当前 Promise。

运行 DTO 放在 `packages/contracts/src/admin.ts`，包含 `id`、`trigger`（manual/scheduled/startup）、`startedAt`、`finishedAt`、整体状态及服务结果。整体状态为 running/succeeded/partial/failed；服务状态为 running/succeeded/failed。状态快照包含可执行状态与原因、当前运行及最近结果；服务结果仅暴露 id、type、label、状态与安全错误摘要。

每个服务 Promise 完成时更新对应结果，整轮 `allSettled` 后形成最终快照。至少一个服务失败且有服务完成为 partial，全部失败为 failed。QQ 空间缺失或缺少必需 Cookie 字段的前置错误改为明确失败，使它进入同一汇总；不借此重构各同步适配器的附件处理。意外协调错误也必须结束运行、记录失败并释放状态，后台 Promise 的拒绝不得无人处理。

手动重复请求返回 409、原因代码与当前 runId；没有启用服务时返回不同原因代码且不生成运行。网络中断造成受理结果未知时，客户端查询状态，不重放 POST。不采用长 HTTP 请求、队列或另起一套手动同步实现。

### 4. 从统一日志入口建立有界快照

新增 `server/src/utils/runtime-logs.ts`，仅负责保留、筛选和读取日志；`logger.ts` 负责将参数和错误安全格式化为单一文本，再统一脱敏，然后同时写入控制台与缓存。保留现有 URL 参数允许列表和错误诊断字段允许列表，补齐消息、堆栈及参数文本中的敏感键、Authorization/Cookie 文本与 URL 凭据处理；不缓存完整异常、请求或响应对象。

固定上限为 500 条，每条消息至多 4096 字符并包含截断标记，脱敏先于截断。记录包含进程内递增 id、ISO 时间、level（info/success/warn/error）、module 和 message。该模块不读取任意服务器文件，也不拦截全局 console；只覆盖现有统一应用日志入口。

`GET /admin/logs` 接受 `level`、`module`、`q`、`limit`。模块精确匹配，关键词对脱敏后的消息忽略大小写匹配。先筛选保留记录，再按时间降序排列并取前 limit 条，时间相同时按 id 降序排列。默认 limit 为 100，有效整数范围为 1–200。客户端每次替换快照，无增量游标、补拉协议或历史分页。

文件持久化不符合已确认的当前进程范围；SSE/WebSocket 会引入连接生命周期和额外鉴权处理，因此采用现有 HTTP 与 SWR 轮询。日志使用纯文本和保留换行的方式显示，明确标注容量及重启清空规则。

### 5. 将读取视角与身份分开，并共享可见性判定

在 `packages/contracts/src/timeline.ts` 为列表和总数增加 `view?: public|admin`。后端使用同一个读取范围判定：只有真实管理员且没有显式请求 public 时才包含私密项。未知值返回 400，未登录用户传 admin 仍只能读取公开内容。

两个路由均先取得可见性条件，再合并服务筛选、搜索的各个 OR 分支，最后查询和计数，避免条件分叉。现有 ORM 已支持 `where`，无需查询后过滤或另建访客接口。

`GlobalContext` 保留真实 `isLoggedIn`，增加当前视角、切换动作、退出动作和用于条目操作的 `canManageItems`。预览为当前页面会话内状态，不写 Cookie 或持久化存储；刷新页面后，依据真实登录态恢复默认视角。进入预览关闭面板，显示“访客预览”与返回入口，并保留退出操作。

`TimelineItemLabel` 使用 `canManageItems` 决定内容管理操作；不能用伪造 `isLoggedIn=false` 实现预览，否则会丢失返回入口并混淆实际权限。

### 6. 利用 SWR 原有能力隔离缓存和控制轮询

将 RootLayout 的登录状态查询放在会话数据缓存边界之外。首屏确认登录状态后才挂载数据子树并发出时间线、总数或管理请求。TimelineHome 外层保留搜索和服务筛选状态，将查询、列表、进度及管理面板组成的数据子树放入按“身份 + 视角”重新挂载的 `SWRConfig`，每个新边界使用独立 Map provider。这样切换数据范围不会销毁筛选条件。项目安装的 SWR 类型已提供 `provider`、`refreshInterval`、`refreshWhenHidden` 和 `keepPreviousData`，无需新增缓存库。

所有时间线列表和总数请求显式带当前 view，切换时重建数据边界，不沿用上一范围的页面数据，也不启用 keepPreviousData；重置分页、当前位置和进度，保留搜索与服务筛选。旧请求即使完成，也只关联已卸载的旧缓存。使用当前 provider 的 scoped mutate 刷新数据，避免全局 mutate 越过边界。

同步页签可见时每 2 秒读取状态。日志页签可见且自动刷新开启时每 5 秒读取快照，支持暂停与手动刷新。模块和关键词输入停止 500 毫秒后更新查询。隐藏页面、面板关闭、页签切换或进入预览时停用对应 key 和轮询。时间线刷新以已观察到或已受理的运行结束为触发条件，每个 runId 只刷新一次当前范围的列表和总数。

退出按钮和现有 URL 退出入口共用一个显式 POST 动作，替换 RootLayout 中以 useSWR 自动发送退出 POST 的流程。从面板发起退出时先关闭模态框。请求成功后确认退出并销毁受限数据边界，失败时在页面统一显示提示与重试按钮。收到既有 `AUTH_EXPIRED_EVENT` 或确认登录失效时，立即关闭面板、恢复公开视角并替换缓存边界，旧响应不能恢复受限数据。

## Risks / Trade-offs

- [仅保存当前进程信息] → 页面明确标注最近运行与日志的保留范围；不将重启前尚未确认结束的任务伪装为成功。
- [同步函数完成不等于所有后台附件处理完成] → 展示执行状态及日志，不提供缺乏依据的数据条数或百分比；QQ 空间明确的前置认证失败必须正确上报。
- [轮询可能遗漏已被淘汰的日志] → 显示固定容量与快照范围，提供暂停和筛选；本次不承诺完整审计历史。
- [Error 堆栈和额外参数仍可能携带凭据] → 统一格式化、脱敏后才双写，增加包含 URL、请求头与嵌套异常的针对性回归用例。
- [视角切换或退出时旧请求晚到] → 独立且重新挂载的缓存 provider，禁止沿用旧数据，并以浏览器回归验证延迟响应场景。
- [多个后端副本的内存状态无法共享] → 本次范围明确为现有单进程部署，不宣称提供跨副本互斥或完整历史。

## Migration Plan

1. 按 tasks.md 分层实现并完成契约、权限、并发、脱敏和缓存隔离验证；不建立数据库迁移或兼容适配层。
2. 客户端和后端作为同一版本一起发布，沿用现有管理员账号与配置；后端重启后运行记录和日志从空状态开始。
3. 验证既有登录、正常同步、内容私密设置及公开读取，再验证新增管理操作。需要回滚时恢复上一组客户端与后端构建；没有新增持久化状态需要回退。
