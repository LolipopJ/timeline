# Design

## Context

动机见 [proposal.md](proposal.md)。当前实现有以下约束：

- `server/src/sync/index.ts` 按来源枚举分发；`coordinator.ts` 已统一定时、启动和手动触发，以 `Promise.allSettled` 隔离来源失败，并在内存保留最近十次运行。
- `getSyncTaskLastExecuteTime` 从最近时间线项的 `updated_at` 推算范围；没有里程碑时无法推进，不能承担奖杯同步检查点。
- `TimelineItem` 以 `sync_service_id + content_id` 唯一，支持管理员私密与软删除。现有 serializer 不输出内部 `metadata`。
- Steam 已有 Web API、Axios 调用及封面地址处理；客户端已有附件、来源菜单、两种主题和静态导出。
- 工作区正在进行 `enhance-timeline-search`。本变更新增条目需接入其统一查询、分享与来源菜单，不另建搜索状态或查询接口。

## Goals / Non-Goals

**Goals:**

- 把平台数据差异限制在三个采集器中，以一个明确的归一化模型计算里程碑、存储并展示。
- 用持久化摘要与检查点降低详情请求，允许必要的轻量目录扫描，并最终发现离线、迟到及集合变化。
- 保持本体完成与最新一次全成就两种稳定身份；系统合并状态不会干扰管理员隐私与删除状态。
- 先完成可运行的 PSN 纵向链路，再接入 Xbox 与 Steam，所有阶段沿用同一套完成判定和展示契约。

**Non-Goals:**

- 不为每个普通奖杯或每次 DLC 补完创建事件，不建设成就管理器、排行榜或跨平台游戏匹配系统。
- 不手工维护本体成就名单，不使用首次快照、名称或 Gamerscore 猜测本体范围，不抓取页面补造历史。
- 不增加授权管理界面、客户端令牌输入框、通用凭据注册器或新的同步调度框架。
- 不把“后续零全库详情扫描”误解为“平台必须支持 since 参数”；不宣称近期游戏列表能覆盖所有历史。

## Decisions

### 1. 三个来源共用一个明确的数据流

`PSN_GAME_ACHIEVEMENT`、`XBOX_GAME_ACHIEVEMENT` 和 `STEAM_GAME_ACHIEVEMENT` 分别扩展现有 `SyncServiceBase`。PSN `accountId` 与 Xbox `xuid` 省略时从授权会话解析数字 ID；Steam 需要显式填写 `steamId`。检查点与内容标识统一使用目标账号的数字 ID。

```text
现有 coordinator
  └─ 平台采集器：授权、目录、成就、时间与可验证的本体证据
       └─ 公共里程碑计算：base / all 两个逻辑位置
            └─ 数据库事务：条目 + 游戏快照 + 成功检查点
                 └─ 既有 serializer / 列表 / 总数
                      └─ 共用游戏成就卡片
```

公共部分采用少量普通类型和函数，平台采集器负责外部输入验证，不增加单实现接口、插件注册器或配置驱动的规则引擎。替代方案是三个采集器分别实现去重与日期规则；会导致 DLC、合并和失败语义漂移，故不采用。

### 2. 按同步任务配置凭据并明确 Python OAuth 会话格式

| 字段                 | 用途与归属                                                                                                                       |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `psnNpsso`           | PSN 初次交换授权的 NPSSO。刷新结果在 `server/.temporary` 下按凭据哈希分别持久化，同一凭据的并发授权复用同一次请求。              |
| `xboxClientId`       | 按上游 README 注册的自有 Microsoft OAuth 应用 ID。                                                                               |
| `xboxClientSecret`   | 同一 OAuth Web 应用的有效 client secret。                                                                                        |
| `xboxTokenStorePath` | Python 库 `OAuth2TokenResponse` JSON 文件的绝对路径，包含匹配应用的 OAuth access/refresh token，由 Python 读取并持久化刷新结果。 |
| `steamWebAPIKey`     | Steam 成就及近期游戏时长任务分别填写各自使用的 Web API Key。                                                                     |

各任务在其 `services` 配置项内提供凭据。多个任务使用同一凭据时，每个任务都需要填写。真实值仅保留在被 Git 忽略的 `server/configs/server.ts` 与私有会话中。查询其他账号受平台权限限制。

PSN 接入 [psn-api 授权流程](https://psn-api.achievements.app/api-docs/authentication)，Steam 沿用 Axios 与官方 Web API。Xbox 改用 [OpenXbox/xbox-webapi-python](https://github.com/OpenXbox/xbox-webapi-python)：首次登录独立使用上游 `xbox-authenticate`，明确指定自有应用、注册回调和会话文件，回调端口与注册 URI 必须一致。首次登录通过该 CLI 支持的临时进程环境传入应用凭据，不把密钥写进命令行；服务端仍从 `server/configs/server.ts` 读取配置。正常采集仅加载会话并调用库的授权刷新能力，不打开浏览器或等待人工输入。

Python 按库的 [`AuthenticationManager`](https://github.com/OpenXbox/xbox-webapi-python/blob/master/xbox/webapi/authentication/manager.py) 建立 OAuth、用户令牌与 XSTS 链路。正常刷新不交换新的 authorization code，不新增服务端回调路由或 redirect URI 配置。只接受该库的 OAuth JSON 文件，不增加旧会话转换、其他令牌格式或另一套授权路径。

### 3. 用异步 Bun.spawn 调用短生命周期 Python 采集器

Xbox 的 TypeScript 入口放在 `server/src/sync/`，只负责调用 Python、校验归一化结果和接入既有公共流程。Python 入口拟放在 `server/python/xbox_collector.py`，使用库提供的异步 `SignedSession`、`AuthenticationManager` 和 `XboxLiveClient`，负责 Xbox 授权、平台请求及数据归一化，不读取数据库或 TypeScript 配置，也不计算或写入时间线里程碑。

```text
Bun Xbox 来源
  ├─ summaries 请求 ─stdin JSON─> Python：标题与成就摘要
  │                   <─stdout JSON─ 目标 XUID 与完整摘要
  ├─ Bun：比较已保存摘要，选择变化、新增及轮转对象
  └─ details 请求 ─stdin JSON─> Python：候选游戏的成就分页
                      <─stdout JSON─ 完整归一化结果
       └─ 既有公共计算、数据库事务与成功检查点
```

每次调用处理一个摘要任务或一批游戏详情，避免每个成就、每款游戏都启动解释器。通常是一轮摘要和一轮候选详情；大基线按有界批次处理，Python 在一次调用内复用 HTTP 会话与授权。常规增量选择仍由 Bun 维护，Python 不额外保存游戏扫描状态。

运行环境统一为 `server/.venv`，使用经验证的 Python 3.12+，按用户的本机约定由 `uv` 管理。Windows 使用其 `Scripts/python.exe`，其他部署平台使用其 `bin/python`；入口和虚拟环境从稳定的 server 根目录定位，不依赖启动工作目录。`server/python/requirements.txt` 固定经验证的 Python 包 `xbox-webapi` 与 HTTP 代理支持版本，通过 `uv pip` 安装到该虚拟环境；JavaScript 继续使用唯一 `bun.lock`，不引入 Poetry 或另一套锁文件。虚拟环境加入忽略规则，不能随源码提交或跨平台复制。

以 [Bun.spawn 官方接口](https://bun.sh/docs/runtime/child-process) 异步启动解释器，使用参数数组和明确的工作目录，固定 UTF-8 编码，不经 shell 拼接命令，也不使用阻塞的 `spawnSync`。协议只有 `summaries` 和 `details` 两个操作：stdin 传入 XUID、OAuth 配置、会话路径和必要的目标游戏标识；stdout 仅在操作完整成功后输出一份对应的 JSON 结果；stderr 仅承载脱敏的错误码与说明。令牌与应用密钥不进入 argv、stdout 或原始异常堆栈。

Bun 并行消费 stdout、stderr 并等待退出，只有零退出码与合法、完整的结果同时成立才继续写入。stdin 在发送完整请求后关闭；超时或取消时终止子进程并等待退出，服务停止继续遵守现有等待同步和资源释放顺序，不调用 `unref` 遗留后台进程。缺少解释器或依赖、错误 JSON、异常退出和部分结果都只使 Xbox 来源失败，不推进成功检查点；错误说明需限长且不转发原始平台响应。

多个来源可能共享一个 Xbox 授权文件，因此同一文件的采集调用在 Bun 端串行执行，失败也必须释放等待队列。Python 持久化刷新后的 OAuth JSON 时使用同目录临时文件和原子替换，避免中断留下半份会话。该写入独立于里程碑数据库事务；平台请求失败不撤销已成功刷新的会话，也不推进数据库成功检查点。

| 方案                         | 取舍                                                                              |
| ---------------------------- | --------------------------------------------------------------------------------- |
| 异步 `Bun.spawn` + JSON 管道 | 采用。沿用服务端已有 Bun 运行时，只增加短生命周期解释器进程，调用与错误边界明确。 |
| `node:child_process.spawn`   | 可行，但当前服务端以 Bun 运行，没有额外的 Node 运行目标；不再包装第二种启动方式。 |
| 常驻 Python HTTP 服务        | 引入端口、独立服务生命周期和部署配置，当前定时批量采集不需要。                    |
| 嵌入 Python 或 FFI           | 增加解释器 ABI、线程与跨平台打包复杂度，不适合这里只需交换结构化数据的边界。      |

Bun 的原生 `ipc` 通道面向 Bun 子进程；这里使用通用标准输入输出，不为 Python 自建 RPC 框架。

### 4. 本体证据是可选的真实数据，不是推测规则

采集器归一化完整的有效成就定义、解锁状态、实际时间、平台游戏 ID、封面，以及可验证的本体证据。PSN 游戏身份包含实际奖杯集合与所用服务标识，不能把 PS4、PS5 或区域版本按名称合并。

- PSN：通过真实白金奖杯类型与其解锁时间记录白金；全成就核验所有奖杯组及完整分页。[接口依据](https://psn-api.achievements.app/api-docs/user-trophies)
- Xbox：Python 库的[成就 provider](https://github.com/OpenXbox/xbox-webapi-python/blob/master/xbox/webapi/api/provider/achievements/__init__.py) 提供现代 Xbox 与 Xbox 360 成就接口，模型包含实际解锁时间；两个接口族的差异在 Python 内归一化。标题历史的便捷接口默认只取 5 项，不能作为完整目录；成就便捷接口也不能当作自动完成分页。优先使用库的 provider；需要补齐分页参数时，复用其已鉴权的 session、请求约定与模型，不另写 OAuth 或签名实现。完整分页和目录覆盖以脱敏真实返回验证。Mythic 的产品规则已由[微软公布](https://news.xbox.com/en-us/2026/09/29/xbox-insiders-october-2026-console-features-4/amp/)，但当前公开模型未表达新本体分组；更换库不等于已经取得本体证据，无法验证时只生成全成就项。
- Steam 使用 [`GetOwnedGames`](https://partner.steamgames.com/doc/webapi/IPlayerService) 发现游戏，并合并任务 `gameOverrides` 中的 AppID。通过 [`GetPlayerAchievements` 和 `GetSchemaForGame`](https://partner.steamgames.com/doc/webapi/ISteamUserStats) 核验完整成就与解锁时间。读取 [Steam 公开成就页](https://partner.steamgames.com/doc/features/achievements/ach_guide?l=english#what_players_see) 的结构化成就集，并核对其 API ID 与 Web API 定义一致。平台未提供明确分组时，配置可提供经过核验的本体 API ID 清单。

无法验证新分组的游戏只计算全成就，这是已确认的产品规则，不增加替代抓取路径。也不使用平台对“已拥有 DLC”或单个集合给出的完成徽章代替完整全成就核验。无法枚举的已移除、退款或借用历史不宣称已经同步。

### 5. 用两个稳定位置保存完成事件

`content_id` 由平台、规范化账号 ID、平台游戏 ID 与 `base | all` 位置确定；复用已有的服务与内容联合唯一约束。真实白金、Mythic 和本体全成就都占用 `base`，全成就占用 `all`。名称、时间和成就数量不进入身份。

| 观察到的数据                 | 写入及展示                                                               |
| ---------------------------- | ------------------------------------------------------------------------ |
| 本体完成，完整集合尚未完成   | 记录本体项。                                                             |
| 没有本体证据，但完整集合完成 | 只记录全成就项。                                                         |
| 本体与整个集合是同次完成     | 保存两个逻辑位置，全成就项标为系统合并，列表只展示本体项；PSN 显示白金。 |
| 稍后补完追加成就             | 保留本体项，更新全成就位置的完成时间及达成时数据，取消系统合并。         |
| 再次追加但未补完             | 保留上次完成事件，不把历史项改成当前进度。                               |

白金时间来自奖杯本身；其他完成时间来自相应完整集合最后的真实解锁。缺失或占位时间不使用当前时间补齐，记录数据限制并留待轮转复查。时间相等只有在来源证据能证明同次完成时才触发合并，不凭低精度秒值猜测先后。

本体项一旦建立不因新的全成就事件改变日期；全成就项仅在新证据证明对应集合再次完成时更新。`from` 限制可创建的里程碑日期，不截断用于判断完成的旧成就。

### 6. 单独持久化来源与游戏状态

在数据库层新增奖杯来源状态和游戏快照两类实体，不借用时间线 metadata 保存调度信息：

- 来源状态按服务与目标账号隔离，保存本次开始、结束、结果、最近成功范围及目录/轮转进度。改变目标账号后使用该账号自己的基线，不继承另一账号的检查点。
- 游戏快照保存稳定游戏身份、摘要签名、成就集合版本或定义指纹、完成判定所需的归一化数据、本体证据及最近核验状态。指纹覆盖成就身份和分组，不只比较数量。
- 任务开始时记录尝试；请求在数据库事务外完成。成功时在同一短事务中写入条目、相关游戏快照和成功检查点。失败只记录本次失败，不推进成功范围。
- 成功水位以本轮开始范围为界；无变化也保存成功。发现逻辑结合摘要与轮转，不把“解锁时间早于水位”当成已经处理过的证明。

替代方案是沿用最近条目的 `updated_at` 或内存运行历史，无法表达零事件成功和重启恢复，故不采用。该状态只服务新奖杯来源，不顺带重构其他采集器。

### 7. 摘要变化与持久化轮转共同发现更新

首次建立接口可枚举范围内的基线；后续详情集合由“新游戏、摘要变化游戏、本轮轮转游戏”组成并去重。轮转使用固定、有界的内部批量与持久化位置，不增加用户配置旋钮。持续成功后每个已知候选游戏都会再次核验，包含已完成游戏。

- PSN 比较标题最近更新时间、已解锁数量与可得的集合版本；完整分页和必要摘要扫描可以继续进行，不能仅凭旧解锁时间提前断言没有迟到数据。
- Xbox 比较游戏摘要的最近解锁时间、已解锁数量和可得版本，再读取候选详情的全部分页。
- Steam 读取必要的轻量游戏目录与游玩摘要，比较新游戏和游玩变化；近期游戏接口只能辅助，轮转承担无游玩变化、延迟上报和长期停机后的补查。

Schema 或分组变化触发重新核验；外部返回完整且无里程碑变化可成功推进。请求失败、限流耗尽重试或分页未完成不能作为成功推进。沿用现有日志与重试工具，使用受控并发，不增加守护进程或消息队列。

### 8. 成就数据、系统合并与管理员操作分开

在 `TimelineItem` 增加可选的、类型明确的归一化成就 JSON 字段，以及默认 `false` 的内部 `achievement_merged` 标记。使用一个独立布尔标记，是为了避免把系统合并误当管理员软删除；`deleted_at` 继续只表达现有删除语义。

每个逻辑位置最多一个实体，系统合并只改变 `achievement_merged`。统一的时间线 where 条件在分页、列表、按 ID 查询与总数之前排除该标记，与现有来源、搜索、私密及软删除条件一起执行。不得在客户端接收后再过滤，否则计数和分页会出错。

采集更新保留已存在条目的管理员 `is_secret` 和 `deleted_at`，新条目使用来源 `secret` 的初值。系统展开不能调用管理员恢复逻辑。服务端 serializer 只投影成就展示字段，隐藏合并标记和游戏快照，不输出原始平台响应。

### 9. 共用一个卡片，延续现有时间线语言

共享契约增加可选的 `achievement` 展示 DTO，包含平台、游戏 ID、`platinum | mythic | base_completion | all_achievements` 类型及可用的达成时数量。游戏名使用 `title`，简短完成文字使用 `content` 以支持既有搜索，封面走 `attachments`，链接走 `url`，实际完成时间走 `created_at`，不重复存储同义展示字段。

```text
现有时间线日期与来源、菜单
┌──────────┬──────────────────────────┐
│          │ 平台图标  PlayStation    │
│ 游戏封面 │ 游戏名称                 │
│          │ 奖杯图标  白金奖杯       │
│          │ 本体完成 · 达成时 54/54  │
└──────────┴──────────────────────────┘
```

Steam 采集使用游戏库竖封面，读取 Steam 发布的素材地址，固定地址为按 AppID 生成的 `library_600x900.jpg`。Steam 成就卡片按 2:3 显示完整封面，桌面约 96×144，窄屏约 64×96。PSN 和 Xbox 封面在桌面约 96×128，窄屏约 64×86。卡片使用 Tailwind 主题变量、共用封面组件及 `@mdi` 平台和奖杯图标，长标题正常换行。白金银蓝、全成就暖金、Mythic 绿色只做点缀，图标和文字共同传达语义。数量明确属于“达成时”，不显示成当前进度条。

图片缺失使用固定比例占位，链接与菜单保留键盘焦点；不引入持续庆祝动画或图片生成依赖。卡片和来源标签接入现有 share/type 菜单，不新增详情路由、Server Action 或浏览器登录状态。

## Risks / Trade-offs

- [Xbox 新增 Python 运行与部署依赖] → 只在启用 Xbox 时要求准备虚拟环境，版本与依赖固定在专用要求文件中；缺失时明确报告来源失败，其他来源继续运行。
- [跨进程结果损坏、阻塞或资源未释放] → 使用单次 JSON 请求响应、并行读取输出和明确的退出/超时清理；通过正常、异常、无效输出和进程回收用例验证边界。
- [多个来源同时刷新一个 OAuth 文件] → 同文件调用串行，刷新结果原子保存；授权应用与会话匹配，不自动切换共享应用或尝试其他会话格式。
- [Xbox Mythic 证据不足，Steam 公开成就页的结构化数据可能变化] → 字段不足时继续按完整的 Web API 定义判定全成就。Steam 本体判定使用经核验的分组或明确配置。
- [接口可能只提供当前集合、部分历史或缺失解锁时间] → 不回填猜测历史，不制造同步时间；将限制写入来源日志与配置说明。
- [摘要未随离线解锁或集合更新变化] → 持久化轮转复查覆盖已知候选游戏，接受最终发现的延迟，不承诺纯时间游标的即时完整性。
- [合并更新与管理员私密、删除冲突] → 分开记录系统合并，事务写入，提供针对隐私、删除、展开和重试的最小回归证据。
- [新增类型和客户端卡片需同时生效] → 正式实现时同批发布服务端、契约和静态客户端，并运行三端类型检查与静态构建。

## Migration Plan

1. 本次仅更新现有规划，保持代码、用户配置和运行行为不变；旧的凭据准备完成标记因 OAuth 模型变更重新打开，不启动服务端或 Python 授权。
2. 正式 apply 阶段补齐 OAuth 配置类型、示例与说明，先在开发库验证新增实体和默认字段，再完成 PSN 纵向链路、Python Xbox 采集和 Steam；不引入旧 schema 兼容层。
3. 启用 Xbox 的部署在目标平台创建 `server/.venv` 并安装固定版本要求，独立完成匹配应用的首次授权，确认会话文件可持久化刷新；只启用其他来源的部署跳过 Python 准备。
4. 部署前备份数据库，同批发布两端，按启用来源建立首次基线。保留 `server/.static`、`server/.temporary` 和 Xbox OAuth JSON 会话文件。
5. 如需回退，使用对应代码与数据库备份，并移除新增来源配置；不自动清理媒体、会话或检查点，不为旧版本添加接口别名或兼容分支。
