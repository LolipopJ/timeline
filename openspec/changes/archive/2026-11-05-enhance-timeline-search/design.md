# Design

## Context

`client/src/components/TimelineHome/index.tsx` 目前用 `useState` 保存 `GetTimelineItemsParams`，只在首次渲染时读一次 `useSearchParams()`，之后通过 `router.replace` 单向写回 URL。组件卸载前的 URL 变化（后退/前进、刷新）不会再进入状态，因此链接只能单向描述筛选，不能作为来源。

搜索框 `client/src/components/TimelineSearch/index.tsx` 目前只有自由文本输入与排序菜单。服务端 `server/src/api/timeline-query.ts` 的 `getTimelineWhere` 已支持 `serviceId` 与 `serviceType` 过滤，但客户端没有任何入口写入 `serviceId`；`serviceType` 参数能从 URL 读入却从未被写入，也没有界面提示。时间线项菜单 `client/src/components/TimelineItemLabel/index.tsx` 只在 `canManageItems` 或条目带 `url` 时才出现。

可见性过滤已在查询阶段生效：`getTimelineWhere` 的 `base` 会在 `search` 的 OR 分支之外附加 `is_secret: false`，列表与总数共用同一函数。列表接口对分页参数做正则与范围校验，非法时返回 400。

约束：客户端是 `output: "export"` 的静态导出，页面为 `Suspense` 包裹的纯客户端交互；不能用服务端渲染或路由处理器承载筛选解析。共享契约 `packages/contracts` 必须保持无框架依赖。

## Goals / Non-Goals

**Goals:**

- 让 URL 成为筛选状态的单一来源，使后退/前进、刷新、粘贴都能恢复同一结果。
- 在不引入新 URL 参数的前提下，用 `search` 参数内的条件语法表达 ID 与来源类型，使链接可以只带一个可读字符串。
- 把条件解析、序列化和可见性判定放在单一位置，避免搜索框、菜单与请求键各自解释一次。

**Non-Goals:**

- 不新增时间线项详情路由或弹窗，不改变现有条目渲染方式。
- 不为 ID 查询新增独立接口；沿用列表与总数接口的过滤参数。
- 不改变既有可见性、软删除、分页与排序语义。
- 不做关键词高亮、搜索建议或跨字段权重排序。
- 不保留旧 `serviceType` URL 参数的兼容读取。

## Decisions

### 用 `search` 参数内的条件语法表达结构化筛选

`id:<uuid>` 与 `type:<serviceId>` 直接写在 `search` 里，而不是新增独立 URL 参数。理由：分享链接只带一个可读字符串；`search` 已是既有参数，服务端只需新增一个 ID 过滤字段，无需为每个条件开新参数。

替代方案：新增 `item=<uuid>` 与 `serviceId=<id>` 参数。缺点是两个条件要各自维护解析、回读与清除路径，且 URL 中出现多个语义重叠的筛选参数；现存的 `serviceType` 参数正是这种设计的遗留物，本次一并移除。

### 由客户端把条件翻译成后端参数

解析只发生在客户端：`type:<serviceId>` 转换为既有的 `serviceId` 请求参数，`id:<uuid>` 转换为新增的按 ID 过滤参数。后端不解析 `search` 内的语法，继续把 `search` 当作普通关键词。

理由：遵循现有架构——路由与查询层只处理已结构化的参数，契约不承载客户端交互语法。若后端解析，`search` 将同时成为关键词和查询语言，两端的解析规则必须永远一致，且普通用户输入的 `type:` 字样会被意外解释。

替代方案：后端解析 `search` 语法。会迫使契约与后端理解展示层语法，并让关键词搜索失去「按字面匹配」的确定性。

### 非法条件退化为关键词，而不是报错

无法解析为 UUID 的 `id:` 与未知的 `type:` 值都当作普通关键词参与搜索。理由：搜索框是自由输入，用户键入 `id:` 时可能正在输入 UUID 前缀，报错会让输入过程中断。只有真正发送到后端的非法 ID 参数（例如手工构造 URL）才由接口返回 400。

### 解析与序列化集中在一个客户端工具模块

新增客户端工具承载：从 `search` 文本提取条件、把条件与关键词组成 `search` 文本、把条件转换为请求参数、判断两个筛选状态是否等价。搜索框、菜单、`TimelineHome` 都使用同一份实现，避免三处各自的 `startsWith("id:")` 逻辑漂移。

### URL 使用 `router.replace` 同步，并回读同一来源

保留现有 `router.replace(..., { scroll: false })` 写入方式（不新增历史记录条目），但把读取改为跟随 `useSearchParams()`：状态从 URL 派生，写入后由新的 URL 再驱动一次渲染。这样后退/前进与粘贴链接都走同一条路径。

替代方案：继续用 `useState` + effect 写回并在 `popstate` 时手动同步。会造成 URL 与状态双份真相，并需要处理写入触发的自身回读（回环）。

### 离散操作绕过防抖

关键词输入保留 500ms 防抖后写 URL，避免每次按键都改写历史；删除标签、只看当前类型、切换排序立即写入。复制分享链接仅生成并复制包含 ID 的链接，不提交任何筛选状态；菜单顺序为打开链接、复制分享链接、只看当前类型。实现上把「立即写入」做成显式提交路径，而不是给 `useDebounce` 加特例，避免防抖延迟影响来源筛选的可见反馈。

键入的结构化条件在空白或 Enter 确认后转换为标签，完整粘贴可立即确认，避免已知 ID 前缀吞掉仍在输入的后缀。输入法合成期间只保留草稿，不安排 URL 提交。提交层保存当前 URL 下的待提交条件，来源菜单通过函数更新合并最新关键词；已过期的异步操作必须在取消计时器前被拒绝。同一关键词语义的 URL 回写保留输入中的空白，不同条件的 URL 导航重置草稿。

### ID 条件与其它条件互斥

写入 ID 时清空关键词与类型，写入关键词或类型时清除 ID。理由：单条结果与常规浏览是两种意图，叠加后几乎总是空结果；互斥让状态与 URL 始终只有一个 ID，语义清晰。

### 类型入口按实际存在的来源提供

「只看当前类型」直接使用条目的 `sync_service_id`，因此天然只覆盖真实存在于时间线中的服务，不会出现枚举里尚未实现的来源。搜索框手动输入未知 `type:` 值时退化为普通关键词。

客户端通过公开的 `GET /timeline-services?view=public|admin` 获取配置服务与当前视角可见、未软删除条目来源的 ID 数组，以识别已知的 `type:` 条件。数据库层对 `sync_service_id` 执行 DISTINCT 查询，路由复用 `getTimelineWhere` 和已验证的管理员 Cookie，不信任 `view=admin` 授权。该接口只返回 ID，不输出服务配置或凭据，使用 `private, no-store`。服务清单按视角隔离缓存，加载完成前不发送时间线查询，避免把尚未识别的条件误当关键词；加载失败时提供重试。清单与时间线查询复用现有 SWR 和 Axios。

### 按 ID 过滤复用现有 where 构造

在 `getTimelineWhere` 的 `base` 里附加 `id` 条件（与 `serviceId`、`is_secret` 同级），天然落在 `search` 的 OR 分支之外，且在分页与计数前生效。路由层对 ID 参数做 UUID 格式校验，非法返回 400。无需新增序列化或响应结构。

## Risks / Trade-offs

- **后退/前进与防抖的竞态**：防抖延迟期间按下后退，可能让尚未提交的关键词覆盖刚恢复的历史状态。→ 在 URL 变化时取消挂起的防抖提交，并让条件解析以当前 URL 为准。
- **`type:` 值包含空格或标点**：服务 ID 可以包含空格、撇号和冒号。→ 在词边界按已知服务 ID 优先匹配最长值，跳过已消费的完整值；输入仍是更长服务 ID 的前缀时不在内部空格处提前确认，未知值仍退化为关键词。
- **移除 `serviceType` URL 参数是破坏性变更**：任何外部保存的旧链接会失去类型筛选。→ 该参数从未由界面写入，仅存在于手写 URL；在 proposal 中标注为 BREAKING，并在文档中说明新的 `type:` 写法。
- **单条结果页与月份分组**：只显示一条时，年份/月份章节与「当前年月」仍需正常显示。→ 沿用现有分组逻辑，不写特例；无结果时走既有空状态。
- **剪贴板权限**：非安全上下文或用户拒绝时 `navigator.clipboard` 不可用。→ 捕获失败并提示，不改变当前 URL 与结果。
- **ID 冲突的解释成本**：分享链接打开后搜索框显示 `id:<uuid>`，读者可能误以为需要自己输入。→ 以标签（含删除按钮）而非原始文本呈现，并在文档与提示中说明。

## Migration Plan

客户端与服务端同批发布：服务端先支持按 ID 过滤参数，客户端再启用 `id:` 条件与菜单入口，避免分享链接在旧后端上得到 400 或空结果。回退时同时回退两端；旧链接中的 `serviceType` 参数在新客户端将不再生效，需要用户改用 `type:` 条件，不提供兼容读取。

无数据库迁移与配置变更。
