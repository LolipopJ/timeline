# Design

## Context

动机见 [proposal.md](proposal.md)。当前实现有以下约束：

- `server/src/sync/index.ts` 按来源枚举分发；`coordinator.ts` 已统一定时、启动和手动触发，以 `Promise.allSettled` 隔离来源失败，并在内存保留最近十次运行。
- `getSyncTaskLastExecuteTime` 从最近时间线项的 `updated_at` 推算范围；没有里程碑时无法推进，不能承担奖杯同步检查点。
- `TimelineItem` 以 `sync_service_id + content_id` 唯一，支持管理员私密与软删除。现有 serializer 不输出内部 `metadata`。
- Steam 已有全局 `steamWebAPIKey`、Axios 调用及封面地址处理；客户端已有附件、来源菜单、两种主题和静态导出。
- 工作区正在进行 `enhance-timeline-search`。本变更新增条目需接入其统一查询、分享与来源菜单，不另建搜索状态或查询接口。

## Goals / Non-Goals

**Goals:**

- 把平台数据差异限制在三个采集器中，以一个明确的归一化模型计算里程碑、存储并展示。
- 用持久化摘要与检查点降低详情请求，允许必要的轻量目录扫描，并最终发现离线、迟到及集合变化。
- 保持本体完成与最新一次全成就两种稳定身份；系统合并状态不会干扰管理员隐私与删除状态。
- 先完成可运行的 PSN 纵向链路，再接入 Xbox 与 Steam，所有阶段沿用同一套完成判定和展示契约。

**Non-Goals:**

- 不为每个普通奖杯或每次 DLC 补完创建事件，不建设成就管理器、排行榜或跨平台游戏匹配系统。
- 不手工维护本体成就名单，不使用首次快照、名称或 Gamerscore 猜测本体范围，不抓取页面补造历史。
- 不增加授权管理界面、客户端令牌输入框、通用凭据注册器或新的同步调度框架。
- 不把“后续零全库详情扫描”误解为“平台必须支持 since 参数”；不宣称近期游戏列表能覆盖所有历史。

## Decisions

### 1. 三个来源共用一个明确的数据流

实现阶段新增 `PSN_GAME_ACHIEVEMENT`、`XBOX_GAME_ACHIEVEMENT` 和 `STEAM_GAME_ACHIEVEMENT`，分别扩展现有 `SyncServiceBase`，目标账号字段为 PSN `accountId`、Xbox `xuid` 和 Steam `steamId`。本次准备不提前把未实现来源放入枚举或服务联合类型。

```text
现有 coordinator
  └─ 平台采集器：授权、目录、成就、时间与可验证的本体证据
       └─ 公共里程碑计算：base / all 两个逻辑位置
            └─ 数据库事务：条目 + 游戏快照 + 成功检查点
                 └─ 既有 serializer / 列表 / 总数
                      └─ 共用游戏成就卡片
```

公共部分采用少量普通类型和函数，平台采集器负责外部输入验证，不增加单实现接口、插件注册器或配置驱动的规则引擎。替代方案是三个采集器分别实现去重与日期规则；会导致 DLC、合并和失败语义漂移，故不采用。

### 2. 沿用服务端顶层凭据，只先准备两个字段

| 字段                          | 用途与归属                                                                                                                          |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `psnNpsso?: string`           | PSN 初次交换授权的 NPSSO。令牌轮换结果写入 `server/.temporary` 下的私有会话，不额外增加 access token 或 refresh token 配置模式。    |
| `xboxTokenStorePath?: string` | 已完成 Microsoft 登录的可刷新 TokenStore 文件绝对路径。授权库读写同一文件，保留轮换后的 refresh token，不把短期 XSTS 当作长期配置。 |
| `steamWebAPIKey?: string`     | 复用已有字段，不新增重复 Steam 令牌参数。                                                                                           |

每个平台先沿用现有全局授权上下文，来源只选择目标账号；不额外设计多套授权上下文的映射。凭据只能访问平台允许当前授权读取的数据。

本次用户明确要求在提案后预填，因此仅修改 `ServerConfig`、注释示例和配置说明；字段标明“预留，尚未启用同步”。真实值由用户填入被忽略的 `server/configs/server.ts`，不写入类型定义、示例或提案。填写这些字段不会触发登录、安装依赖或启动采集。

PSN 接入 [psn-api 授权流程](https://psn-api.achievements.app/api-docs/authentication)，持久化刷新结果与有效期；更换初始凭据后重新建立对应授权。Xbox 使用 [`xbox-webapi`](https://github.com/unknownskl/xbox-webapi-node) 及其作者的 [`xal-node`](https://unknownskl.github.io/xal-node/docs/cli)，后者负责可刷新的会话，前者接收 `uhs` 与 web token。Steam 沿用 Axios 与官方 Web API。依赖只在正式接入时添加。

### 3. 本体证据是可选的真实数据，不是推测规则

采集器归一化完整的有效成就定义、解锁状态、实际时间、平台游戏 ID、封面，以及可验证的本体证据。PSN 游戏身份包含实际奖杯集合与所用服务标识，不能把 PS4、PS5 或区域版本按名称合并。

- PSN：通过真实白金奖杯类型与其解锁时间记录白金；全成就核验所有奖杯组及完整分页。[接口依据](https://psn-api.achievements.app/api-docs/user-trophies)
- Xbox：已有接口可取成就详情及解锁时间；Mythic 的产品规则已由[微软公布](https://news.xbox.com/en-us/2026/09/29/xbox-insiders-october-2026-console-features-4/amp/)，但指定库当前类型没有新分组，必须以授权后的实际返回验证其本体集合和时间。只返回总分不构成本体证据。
- Steam：使用 [`GetOwnedGames`](https://partner.steamgames.com/doc/webapi/IPlayerService) 发现可枚举游戏，以 [`GetPlayerAchievements` 与 `GetSchemaForGame`](https://partner.steamgames.com/doc/webapi/ISteamUserStats) 核验成就。[Achievement Sets](https://partner.steamgames.com/doc/features/achievements/ach_guide?l=english) 仍在测试；仅当实际官方接口能明确提供本体归属时使用该分组。

无法验证新分组的游戏只计算全成就，这是已确认的产品规则，不增加替代抓取路径。也不使用平台对“已拥有 DLC”或单个集合给出的完成徽章代替完整全成就核验。无法枚举的已移除、退款或借用历史不宣称已经同步。

### 4. 用两个稳定位置保存完成事件

`content_id` 由平台、规范化账号 ID、平台游戏 ID 与 `base | all` 位置确定；复用已有的服务与内容联合唯一约束。真实白金、Mythic 和本体全成就都占用 `base`，全成就占用 `all`。名称、时间和成就数量不进入身份。

| 观察到的数据                 | 写入及展示                                                               |
| ---------------------------- | ------------------------------------------------------------------------ |
| 本体完成，完整集合尚未完成   | 记录本体项。                                                             |
| 没有本体证据，但完整集合完成 | 只记录全成就项。                                                         |
| 本体与整个集合是同次完成     | 保存两个逻辑位置，全成就项标为系统合并，列表只展示本体项；PSN 显示白金。 |
| 稍后补完追加成就             | 保留本体项，更新全成就位置的完成时间及达成时数据，取消系统合并。         |
| 再次追加但未补完             | 保留上次完成事件，不把历史项改成当前进度。                               |

白金时间来自奖杯本身；其他完成时间来自相应完整集合最后的真实解锁。缺失或占位时间不使用当前时间补齐，记录数据限制并留待轮转复查。时间相等只有在来源证据能证明同次完成时才触发合并，不凭低精度秒值猜测先后。

本体项一旦建立不因新的全成就事件改变日期；全成就项仅在新证据证明对应集合再次完成时更新。`from` 限制可创建的里程碑日期，不截断用于判断完成的旧成就。

### 5. 单独持久化来源与游戏状态

在数据库层新增奖杯来源状态和游戏快照两类实体，不借用时间线 metadata 保存调度信息：

- 来源状态按服务与目标账号隔离，保存本次开始、结束、结果、最近成功范围及目录/轮转进度。改变目标账号后使用该账号自己的基线，不继承另一账号的检查点。
- 游戏快照保存稳定游戏身份、摘要签名、成就集合版本或定义指纹、完成判定所需的归一化数据、本体证据及最近核验状态。指纹覆盖成就身份和分组，不只比较数量。
- 任务开始时记录尝试；请求在数据库事务外完成。成功时在同一短事务中写入条目、相关游戏快照和成功检查点。失败只记录本次失败，不推进成功范围。
- 成功水位以本轮开始范围为界；无变化也保存成功。发现逻辑结合摘要与轮转，不把“解锁时间早于水位”当成已经处理过的证明。

替代方案是沿用最近条目的 `updated_at` 或内存运行历史，无法表达零事件成功和重启恢复，故不采用。该状态只服务新奖杯来源，不顺带重构其他采集器。

### 6. 摘要变化与持久化轮转共同发现更新

首次建立接口可枚举范围内的基线；后续详情集合由“新游戏、摘要变化游戏、本轮轮转游戏”组成并去重。轮转使用固定、有界的内部批量与持久化位置，不增加用户配置旋钮。持续成功后每个已知候选游戏都会再次核验，包含已完成游戏。

- PSN 比较标题最近更新时间、已解锁数量与可得的集合版本；完整分页和必要摘要扫描可以继续进行，不能仅凭旧解锁时间提前断言没有迟到数据。
- Xbox 比较游戏摘要的最近解锁时间、已解锁数量和可得版本，再读取候选详情的全部分页。
- Steam 读取必要的轻量游戏目录与游玩摘要，比较新游戏和游玩变化；近期游戏接口只能辅助，轮转承担无游玩变化、延迟上报和长期停机后的补查。

Schema 或分组变化触发重新核验；外部返回完整且无里程碑变化可成功推进。请求失败、限流耗尽重试或分页未完成不能作为成功推进。沿用现有日志与重试工具，使用受控并发，不增加守护进程或消息队列。

### 7. 成就数据、系统合并与管理员操作分开

在 `TimelineItem` 增加可选的、类型明确的归一化成就 JSON 字段，以及默认 `false` 的内部 `achievement_merged` 标记。使用一个独立布尔标记，是为了避免把系统合并误当管理员软删除；`deleted_at` 继续只表达现有删除语义。

每个逻辑位置最多一个实体，系统合并只改变 `achievement_merged`。统一的时间线 where 条件在分页、列表、按 ID 查询与总数之前排除该标记，与现有来源、搜索、私密及软删除条件一起执行。不得在客户端接收后再过滤，否则计数和分页会出错。

采集更新保留已存在条目的管理员 `is_secret` 和 `deleted_at`，新条目使用来源 `secret` 的初值。系统展开不能调用管理员恢复逻辑。服务端 serializer 只投影成就展示字段，隐藏合并标记和游戏快照，不输出原始平台响应。

### 8. 共用一个卡片，延续现有时间线语言

共享契约增加可选的 `achievement` 展示 DTO，包含平台、游戏 ID、`platinum | mythic | base_completion | all_achievements` 类型及可用的达成时数量。游戏名使用 `title`，简短完成文字使用 `content` 以支持既有搜索，封面走 `attachments`，链接走 `url`，实际完成时间走 `created_at`，不重复存储同义展示字段。

```text
现有时间线日期与来源、菜单
┌──────────┬──────────────────────────┐
│          │ 平台图标  PlayStation    │
│ 游戏封面 │ 游戏名称                 │
│          │ 奖杯图标  白金奖杯       │
│          │ 本体完成 · 达成时 54/54  │
└──────────┴──────────────────────────┘
```

桌面封面约 96×128，窄屏缩至约 64×86，长标题正常换行。复用现有 Tailwind 主题变量、Image 组件、`@mdi` 平台及奖杯图标；纸张主题保持暖纸底，深色主题保持墨色背景。白金银蓝、全成就暖金、Mythic 绿色只做点缀，图标和文字共同传达语义。数量明确属于“达成时”，不显示成当前进度条。

图片缺失使用固定比例占位，链接与菜单保留键盘焦点；不引入持续庆祝动画或图片生成依赖。卡片和来源标签接入现有 share/type 菜单，不新增详情路由、Server Action 或浏览器登录状态。

## Risks / Trade-offs

- [Xbox Mythic 与 Steam Sets 的字段未获真实账号验证] → 实现时保存脱敏样本并验证本体证据；字段不足的游戏继续按已确认规则只生成全成就，不用未知接口作必需路径。
- [接口可能只提供当前集合、部分历史或缺失解锁时间] → 不回填猜测历史，不制造同步时间；将限制写入来源日志与配置说明。
- [摘要未随离线解锁或集合更新变化] → 持久化轮转复查覆盖已知候选游戏，接受最终发现的延迟，不承诺纯时间游标的即时完整性。
- [合并更新与管理员私密、删除冲突] → 分开记录系统合并，事务写入，提供针对隐私、删除、展开和重试的最小回归证据。
- [新增类型和客户端卡片需同时生效] → 正式实现时同批发布服务端、契约和静态客户端，并运行三端类型检查与静态构建。

## Migration Plan

1. 本次仅完成规划和用户额外授权的凭据类型、示例及文档准备；保持来源列表与运行行为不变，不启动服务端。
2. 正式 apply 阶段先在开发库验证新增实体和默认字段，再完成 PSN 纵向链路、Xbox、Steam 与共用卡片；不引入旧 schema 兼容层。
3. 部署前备份数据库，同批发布两端，按启用来源建立首次基线。保留 `server/.static`、`server/.temporary` 和 Xbox TokenStore 文件。
4. 如需回退，使用对应代码与数据库备份，并移除新增来源配置；不自动清理媒体、会话或检查点，不为旧版本添加接口别名或兼容分支。

## Open Questions

- 使用用户预填授权后，Xbox 返回的新分组与 Steam 官方成就集合具体具备哪些身份、归属及时间字段？这只决定哪些游戏具备本体证据，不改变规格和既定全成就路径。
- 正式安装时哪个已发布版本同时满足这些库的接口与当前 Bun/Node 环境？接入任务验证类型和只读调用，再记录锁文件版本，不预先承诺未验证版本。
